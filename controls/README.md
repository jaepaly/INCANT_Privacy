# 통제 (Controls)

Finding에 대응하는 통제의 참조 구현입니다.

```text
Risk (Finding)  →  Control  →  Evidence  →  재평가
```

문서에 "이렇게 하면 됩니다"라고 쓰는 것과 **실제로 동작하는 코드와 통과한 테스트를
제시하는 것**은 다릅니다. 이 디렉터리가 그 차이를 담당합니다.

---

## CTRL-001 · 전송 전 개인정보 필터

| | |
|---|---|
| 대응 Finding | [`F-005`](../docs/as-is/02_findings_asis.md) 자유 텍스트를 통한 개인정보 비의도적 유입 |
| 대응 룰 | `KR-SPC-001` (개인정보 보호법 제23조 제1항) |
| 구현 | [`controls/pii_filter/`](pii_filter/) |
| 증적 | [`tests/test_pii_filter.py`](../tests/test_pii_filter.py) — **35건 통과** |
| 적용 대상 | 자유 입력 채널 `CH-01`(주문 입력창), `CH-02`(고객센터 문의) |

```bash
python -m pytest tests/ -q
```

### 무엇을 탐지하는가

**"그 자체로 식별 가능하거나 법이 특별히 규정한 정형 식별자"만** 탐지합니다.

| 탐지기 | 분류 | 검증식 | 조치 |
|---|---|---|---|
| 주민등록번호 | 고유식별정보 | 생년월일 + 검사숫자 | **차단** |
| 외국인등록번호 | 고유식별정보 | 생년월일 (검사숫자 미적용 — U-13) | **차단** |
| 신용카드번호 | 금융정보 | Luhn | **차단** |
| 휴대전화번호 | 연락처 | — | 마스킹 |
| 이메일 주소 | 연락처 | — | 마스킹 |

### 무엇을 탐지하지 않는가 — 그리고 왜인가

**성명, 건강 관련 표현, 그 밖의 비정형 정보는 탐지하지 않습니다.**

F-005의 식별가능성 분석에서 나온 결론입니다. 성명 문자열만으로는 특정 개인을 알아볼
수 없고 결합할 정보도 없으므로 개인정보로 보기 어렵습니다. 이름을 잡으려 들면
게임 맥락에서 오탐만 커집니다.

이 판단은 테스트로 고정되어 있습니다 — `test_personal_names_are_not_detected`.
나중에 누군가 "이름도 잡아야 하지 않나"라고 생각해 조용히 바꾸면 테스트가 막습니다.

### 설계 원칙 셋

**① 마스킹은 문장의 의미를 보존한다**

필터 출력은 곧바로 LLM 판정기로 들어갑니다. 마스킹이 문장을 부수면 통제가 게임 기능을
파괴한 것이고, 그러면 통제가 꺼집니다.

```text
"010-1234-5678 번호로 화염구를 세 번 던져라"
  → "010-****-**** 번호로 화염구를 세 번 던져라"
```

**② 감사 기록에 원문을 남기지 않는다**

개인정보 유출을 막는 필터가 그 개인정보를 로그에 적으면 위험을 옮긴 것에 불과합니다.
무엇이 몇 개 탐지되었는지만 남기고 값은 남기지 않습니다.
`test_audit_record_contains_no_personal_data`가 이를 검증합니다.

**③ 차단은 조용히 하지 않는다**

이유를 모르면 이용자는 게임이 고장난 것으로 인식하고 우회를 시도합니다.

### 오탐을 줄이는 방법 — 검증식

정규식만 쓰지 않습니다. 형식이 맞아도 **검증식을 통과해야** 탐지로 인정합니다.

게임 주문에는 숫자가 자주 들어갑니다("레벨 99999999999999 마법", "2026년의 종말").
검증식이 없으면 이런 것들이 걸려 통제가 못 쓰게 됩니다.

정상 주문 12종에 대한 오탐 테스트를 두었고, 검증식을 통과하지 못하는 값
(검사숫자 오류, 13월·32일 등)이 탐지되지 않음을 별도로 검증합니다.

## Risk → Control → Evidence → 재평가

**통제를 인벤토리에 반영하고 엔진을 다시 돌린 결과입니다.**

`inventory/incant_tobe.yaml`의 `CH-01`·`CH-02`에 `pii_prefilter: CTRL-001`을 설정했습니다.

| | 통제 반영 전 | 반영 후 |
|---|---|---|
| 발동 룰 | 12 / 12 | **11** / 12 |
| Finding 후보 | 70건 | **68건** |
| `KR-SPC-001` | CH-01, CH-02 발동 | **발동하지 않음** |
| `EU-SPC-001` | CH-01, CH-02 발동 | **여전히 발동** |

### 왜 EU 쪽은 닫히지 않는가

**이 통제는 GDPR Art.9 특별범주 정보를 다루지 않기 때문입니다.**

Art.9가 열거하는 것 — 인종·민족적 출신, 정치적 견해, 종교적·철학적 신념, 노동조합
가입, 유전자정보, 생체인식정보, 건강, 성생활·성적 지향 — 은 **정형 패턴이 아닙니다.**
정규식과 검사숫자로 잡을 수 있는 종류가 아닙니다.

그래서 인벤토리에서 `special_category_filter`는 `null`로 두었고, `EU-SPC-001`은
계속 발동합니다. 이것은 엔진의 오류가 아니라 **통제 범위의 정직한 표현**입니다.

> 통제 하나로 두 관할이 동시에 닫히지 않는다는 사실이 엔진 출력에 그대로 드러납니다.
> 관할 축을 둔 목적이 이런 지점을 보이게 하는 것이었습니다.

### 남은 과제

`EU-SPC-001`을 닫으려면 패턴 탐지가 아닌 다른 접근이 필요합니다.

| 방향 | 검토 |
|---|---|
| 분류 모델 | 오탐·미탐 관리가 어렵고, 판단 근거를 설명하기 어려움 |
| 저장 제외 | 서비스 모델 §5.4에서 이미 채택 — 원문 미보관으로 저장 측 위험은 제거됨. **전송 측은 남음** |
| 전송 최소화 | 판정에 필요한 최소 형태로 변환해 보내는 설계 |

현재는 **저장 측만 해소된 상태**이며, 전송 측은 미해결로 남겨 둡니다.
해결한 척하지 않는 것이 이 문서의 목적 중 하나입니다.
