# 룰 적용 결과

`tools/run_rules.py`가 룰 카탈로그를 인벤토리에 적용해 생성합니다.

```bash
python tools/run_rules.py           # 생성
python tools/run_rules.py --check   # 동기화 검증 (CI용)
```

| 파일 | 내용 |
|---|---|
| `findings_asis.md` / `.json` | As-Is(실제 배포 데모) 적용 결과 |
| `findings_tobe.md` / `.json` | To-Be(상용화 가정) 적용 결과 |

**전부 생성물입니다. 직접 수정하지 마세요.**

---

## 엔진이 하는 일과 하지 않는 일

이 구분이 이 프로젝트에서 가장 중요한 설계 결정입니다.

| | 엔진 | 사람 |
|---|---|---|
| 룰 술어가 참이 되는 지점 찾기 | **한다** | |
| 발동 근거(어느 필드가 왜) 제시 | **한다** | |
| 근거 조문 연결 | **한다** | |
| 위험도 산정 (Likelihood × Impact) | | **한다** |
| 리스크 시나리오 작성 | | **한다** |
| 개선 우선순위 결정 | | **한다** |
| 판단 보류 항목 관리 | | **한다** |

엔진의 출력은 **Finding 후보**입니다. 사람이 위험도와 맥락을 붙여야 Finding이 됩니다.

**Likelihood는 인벤토리에 없는 정보입니다.** 유입 가능성, 결합 가능 정보의 양,
서비스 규모, 이용자 행동 패턴 같은 것들은 구조화된 필드로 환원되지 않습니다.
이걸 엔진이 하는 척하면 그럴듯하지만 틀린 숫자가 나옵니다.

## 현재 결과

| | 평가 룰 | 발동 룰 | Finding 후보 |
|---|---|---|---|
| As-Is | 12 | **12** | 38 |
| To-Be | 12 | **12** | 70 |

### As-Is — 손으로 쓴 Finding과 대조

[`docs/as-is/02_findings_asis.md`](../docs/as-is/02_findings_asis.md)는 엔진 없이 손으로
작성한 것입니다. 엔진 결과와 비교하면:

| | 손 | 엔진 |
|---|---|---|
| 발동 룰 | 12/12 | 12/12 — **일치** |
| 건수 | 6건 | 38건 |
| 단위 | **이슈** (같은 사실이 KR·EU 룰에 걸리면 하나로 묶음) | **대상** (룰 × 엔티티) |

**발동 룰 집합이 정확히 일치합니다.** 손으로 한 분석이 재현 가능하다는 뜻입니다.

건수 차이는 오류가 아니라 단위 차이입니다. 엔진은 `KR-RET-001`이 11개 데이터 항목
각각에서 참이 되는 것을 11건으로 세고, 사람은 그것을 "보유기간 미정의"라는 이슈 하나로
묶습니다. 개선 조치가 하나이기 때문입니다.

### 엔진과 사람의 판정이 갈리는 지점 — `KR-SPC-001`

**이 사례가 위 표의 구분을 가장 잘 보여줍니다.**

| | 판정 |
|---|---|
| 엔진 | `KR-SPC-001` 발동 (CH-A1), 기본 심각도 **HIGH** |
| 사람 (`F-005`) | 최종 위험도 **LOW** |

**엔진이 틀린 것이 아닙니다.** `severity_base`는 **룰 자체의 기본 심각도**입니다 —
제23조 제1항이 원칙적 금지 구조라는 사실에서 나옵니다. 반면 `F-005`의 LOW는
**이 대상에서의 Likelihood**를 평가한 결과입니다:

- 입력이 60자로 제한되고 목적 지향적이다
- 계정·닉네임·지속 식별자가 없어 결합 용이성을 충족하기 어렵다
- 따라서 식별 가능한 정보가 유입될 확률이 낮다

이 판단은 인벤토리에 인코딩되어 있지 않습니다. **일부는 인코딩할 수 있습니다** —
예를 들어 `service.has_persistent_identifier` 같은 필드를 두고 Likelihood 보정에 쓸 수
있습니다. 다만 "60자 제한이 개인적 서술을 억제한다" 같은 판단은 구조화하기 어렵습니다.

→ 현재는 **엔진이 후보를 내고 사람이 위험도를 붙이는** 구조를 유지합니다.
Likelihood 자동 산정은 하지 않습니다.

### To-Be — 12개 룰이 전부 발동하는 이유

**To-Be는 설계이지 구현이 아닙니다.** 처리방침을 쓰기로 결정했지만 아직 쓰지 않았고,
파기 로직을 넣기로 했지만 아직 없습니다. 인벤토리의 해당 필드가 `null`인 이유입니다.

따라서 To-Be의 Finding 후보 70건은 **위반 목록이 아니라 구현해야 할 통제의 목록**입니다.
통제가 구현될 때마다 인벤토리 필드가 채워지고 해당 후보가 사라집니다.

즉 이 리포트는 **잔여 과제 추적기**로 동작합니다. 그것이 To-Be에서 엔진을 돌리는 이유입니다.

## 관할 조건부 판정

As-Is의 `service`에는 다음이 들어 있습니다.

```yaml
jurisdictions: [KR]
jurisdictions_conditional: [EU]   # Art.3(2) 대상성 미확정 — U-05
```

EU 룰은 평가되지만 결과에 **조건부** 표시가 붙습니다. GDPR이 현 상태의 데모에 적용되는지
자체가 확정되지 않았기 때문입니다(U-05). 조건부 판정을 위반 사실로 기재하지 않습니다.

To-Be는 스토어 출시·다국어 지원을 전제하므로 `jurisdictions: [KR, EU]`로 두어
무조건부로 평가합니다.

## 알려진 한계

1. **`EU-TRP-001`의 보관기간 판단 가능성 조건은 아직 실행되지 않습니다.** WP260 rev.01이 요구하는 "포괄 문구는 불충분" 판정은 처리방침 텍스트를 대상으로 하는데, 인벤토리에 처리방침 본문이 없습니다. 현재는 `privacy_notice_eu`의 존재 여부만 봅니다. `condition_human`에는 온전한 기준이 적혀 있습니다.
2. **`EU-RET-001`은 실제 보관 실태를 볼 수 없습니다.** Art.5(1)(e)는 실제로 필요 기간을 넘겨 보관하는지를 묻는데, 인벤토리는 "정책상 몇 년으로 정했는가"만 담습니다. 시스템·DB 실사가 필요합니다.
3. **필드명 정합이 완결되지 않았습니다.** 룰과 인벤토리 사이의 대응은 [`inventory/README.md`](../inventory/README.md)에 표로 기록되어 있습니다.
