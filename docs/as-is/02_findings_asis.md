## 도출 방식

**Finding은 이슈 단위입니다.** 같은 사실이 국내 룰과 EU 룰에 동시에 걸리면 별개의
Finding으로 쪼개지 않고 하나의 Finding에 근거 룰을 둘 다 답니다. 개선 조치가 하나이기
때문입니다. 대신 관할별로 요구 수준이 다르면 그 차이를 Finding 안에 적습니다.

현재 Finding은 **손으로 작성**했습니다. 룰의 `check_expr`가 아직 실행되지 않기
때문입니다(평가 데이터 모델 미확정). 데이터 모델이 확정되면 이 문서는 생성물로
전환합니다.

## 위험도 산정

`Risk = Likelihood × Impact`

- **Likelihood** — 통제 부재가 실제 문제로 이어질 가능성
- **Impact** — 이어졌을 때의 영향

| | Impact: Low | Medium | High |
|---|---|---|---|
| **Likelihood: High** | MEDIUM | HIGH | CRITICAL |
| **Medium** | LOW | MEDIUM | HIGH |
| **Low** | LOW | LOW | MEDIUM |

### 규모에 대한 주의

INCANT은 해커톤 제출용 데모로 이용자 규모가 매우 작습니다. 이는 **사실상의 완화
요소이지 통제가 아닙니다.** 따라서 Likelihood는 이용자 수가 아니라 **시스템 구조**를
기준으로 평가했습니다. 규모가 커지면 그대로 실현되는 결손이기 때문입니다.

현재 규모를 반영한 실질 위험은 각 Finding의 `현재 규모 고려` 항에 별도로 적었습니다.

### EU 관할 판정의 조건부 성격

GDPR이 현 상태의 INCANT에 적용되는지 자체가 확정되지 않았습니다(Art.3(2) 대상성 —
[VERIFICATION_LOG.md](../../rules/VERIFICATION_LOG.md) U-05). 아래 EU 근거는
**"GDPR이 적용된다고 가정할 경우"** 로만 읽어야 하며, 위반 사실로 기재하지 않습니다.
위험도 등급은 국내 관할 기준으로 산정했습니다.

## F-002 · 국외 이전 근거·고지 부재

| | |
|---|---|
| **위험도** | **CRITICAL** (Likelihood: High × Impact: High) |
| 상태 | OPEN |
| 대상 | A-01, A-02, A-03, A-04, C-01 |
| 국내 근거 | `KR-TRF-001` — 개인정보 보호법 제28조의8 제1항·제2항 |
| EU 근거 (조건부) | `EU-TRF-001` — GDPR Art.44, Art.45, Art.46 |

### 확인된 사실

이용자가 입력한 문장이 판정을 위해 Google(미국)으로 전송됩니다. 프록시는 입력을 60자로
절단해 판정 프롬프트에 붙여 `generativelanguage.googleapis.com`으로 보냅니다
([worker.js#L421](https://github.com/jaepaly/NHN-Project/blob/852bbd544133f840d972cfc667d17a16618d10db/proxy/worker.js#L421),
[worker.js#L484](https://github.com/jaepaly/NHN-Project/blob/852bbd544133f840d972cfc667d17a16618d10db/proxy/worker.js#L484)).
보스 대사(A-03)와 진화 작명(A-04)도 입력 파생 데이터를 같은 경로로 내보냅니다.

이전 근거(제28조의8 제1항 각 호)가 확인되지 않고, 제2항 각 호의 고지사항 5개 중 어느
것도 이용자에게 제공되지 않습니다.

### 리스크 시나리오

이용자가 "우리 엄마 김○○ 병원비 좀 어떻게 해줘" 같은 문장을 주문으로 입력하면, 그
문장이 그대로 국외 사업자에게 전송됩니다. 이용자는 자신의 입력이 국외로 나간다는 사실도,
어떤 사업자에게 가는지도, 거부할 수 있다는 것도 알 수 없습니다.

전송 대상이 자유 텍스트이므로 **무엇이 이전되는지 사전에 특정할 수 없다는 점**이 이
Finding을 다른 항목과 구별합니다.

### 위험도 근거

- Likelihood **High** — 판정 요청마다 발생하며, 이미 상시 발생 중입니다
- Impact **High** — 이전 근거 부재는 예외 요건 미충족이며, 고지 미비처럼 사후 보완으로 치유되는 성격이 아닙니다. 이전 내용의 범위를 특정할 수 없다는 점도 가중 요소입니다

### 현재 규모 고려

이용자 수가 적어 절대적 노출량은 작습니다. 다만 이 항목은 노출량이 아니라 **구조적
근거 부재**가 문제이므로 등급을 낮추지 않았습니다.

### 개선 권고

1. 제28조의8 제1항 각 호 중 어느 근거로 이전하는지 확정
2. 제2항 각 호 5개 고지사항을 갖춘 국외 이전 현황표 작성
3. 처리방침에 국외 이전 항목 반영 및 **이전 거부 방법·절차** 제공
4. Google과의 데이터 처리 조건 확인 (입력 보관·학습 이용 여부 — U-01)

> **설계 쟁점**: 제2항 제5호가 요구하는 '이전 거부'는 이 서비스에서 곧 기능 미제공을
> 뜻합니다. 판정 자체가 외부 LLM에 의존하기 때문입니다. 거부 시 로컬 판정(MockJudge)으로
> 폴백할지, 기능을 제한할지가 To-Be 설계 결정이 됩니다.

### 요구 증적

- 국외 이전 현황표 (제2항 각 호 항목별 대조)
- 이전 근거 확보 문서 / Google 데이터 처리 조건 사본
- 처리방침 내 국외 이전 고지 문구 및 거부 절차 화면

### 관할 차이

EU 관점에서는 **재이전(onward transfer)** 이 추가 쟁점입니다. Art.44 원문이 Chapter V의
조건을 재이전에도 적용한다고 명시하므로, EU 정보주체 → 국내 서비스 → 미국 사업자
연쇄에서 두 번째 구간을 검토 대상에서 뺄 수 없습니다. 한국 적정성 결정(Decision (EU)
2022/254)이 이 구간을 어느 범위까지 커버하는지는 미해결입니다(U-06).

## F-001 · 개인정보 처리방침 부재

| | |
|---|---|
| **위험도** | **HIGH** (Likelihood: High × Impact: Medium) |
| 상태 | OPEN |
| 대상 | 전 항목 (A-01~A-05, B-01~B-05, C-01) |
| 국내 근거 | `KR-TRP-001` — 개인정보 보호법 제30조 제1항·제2항 |
| EU 근거 (조건부) | `EU-TRP-001` — GDPR Art.12(1), Art.13 |

### 확인된 사실

개인정보를 처리하면서 처리방침이 존재하지 않습니다. 게임 내에도, 배포 페이지에도 개인정보
처리에 관한 어떤 고지도 없습니다.

### 리스크 시나리오

이용자는 자신의 입력이 저장된다는 사실, 외부로 전송된다는 사실, 어디에 얼마나 남는지를
알 수 없습니다. 알 수 없으므로 삭제를 요구할 동기도, 방법도 생기지 않습니다.

### 위험도 근거

- Likelihood **High** — 이미 발생 중인 상태입니다
- Impact **Medium** — 그 자체로 직접적 피해를 만들기보다는, 다른 의무(국외이전 고지·보유기간 고지·권리행사 안내)가 실려 나갈 매체가 없어지는 **선행 결손**입니다

### 현재 규모 고려

규모와 무관하게 성립하는 의무입니다. 등급 조정 없음.

### 개선 권고

1. 제30조 제1항 각 호의 법정 기재사항을 포함한 처리방침 수립
2. 타이틀 화면 및 최초 실행 시 상시 접근 가능한 경로 제공
3. 개정 이력 관리 체계 수립

**이 Finding을 먼저 해소해야 F-002·F-003·F-004가 실질적으로 개선됩니다.** 국외이전 고지,
보유기간, 권리행사 방법이 모두 처리방침을 매체로 삼기 때문입니다.

### 요구 증적

- 게시된 처리방침 URL 및 최초 게시일
- 제30조 제1항 각 호 기재사항 대조표
- 서비스 내 접근 경로 스크린샷

### 관할 차이

★ **동일한 '부재' 상태이지만 채워야 할 항목 수가 다릅니다.** GDPR Art.13은 국내 제30조보다
열거가 구체적입니다 — 수령인 또는 수령인의 범주, 제3국 이전 근거(적정성 결정 또는 적절한
안전조치), 보관기간 또는 산정 기준, 감독기구 불만제기권 등.

To-Be에서 문서를 하나만 만든다면 **KR·EU 요구 항목의 합집합**으로 설계하고 관할별로
노출을 분기하는 구조가 필요합니다.

## F-003 · 보유기간 미정의 및 파기 절차 부재

| | |
|---|---|
| **위험도** | **HIGH** (Likelihood: High × Impact: Medium) |
| 상태 | OPEN |
| 대상 | A-05, B-01, B-02, B-03, B-04, B-05 |
| 국내 근거 | `KR-RET-001` — 개인정보 보호법 제21조 제1항, 시행령 제16조 |
| EU 근거 (조건부) | `EU-RET-001` — GDPR Art.5(1)(e), Art.5(2) |

### 확인된 사실

**이용자 입력 원문(`rawText`)이 단말 localStorage에 무기한 남습니다**
([grimoire.ts#L30-L44](https://github.com/jaepaly/NHN-Project/blob/852bbd544133f840d972cfc667d17a16618d10db/src/spell/grimoire.ts#L30-L44)).
localStorage 8개 키 어디에도 만료나 파기 로직이 없고, 항목별 보유기간이 정의된 문서도
없습니다.

### 리스크 시나리오

이용자가 몇 달 전 무심코 입력한 문장이 브라우저에 그대로 남아 있습니다. 공용 PC나 공유
단말에서 플레이한 경우, 다음 이용자가 개발자도구로 이전 이용자의 입력 이력 전체를 열람할
수 있습니다.

### 위험도 근거

- Likelihood **High** — 저장 시점부터 상시 성립하며 이미 발생 중입니다
- Impact **Medium** — 저장 위치가 이용자 단말이라 서버 측 대량 유출면이 없습니다. 다만 공용 단말 시나리오에서는 실질적 노출이 발생합니다

### 현재 규모 고려

단말 저장이므로 규모와 무관하게 이용자 개인 단위로 성립합니다. 등급 조정 없음.

### 개선 권고

1. 항목별 보유기간 정의 및 산정 근거 문서화
2. 보유기간 경과 데이터의 자동 파기 구현 — 시행령 제16조의 복원 불가능한 방법
3. 파기 실행 기록 확보 방안 수립

### 요구 증적

- 항목별 보유기간 정의표
- 파기 로직 구현 코드 및 테스트 결과
- 파기 실행 로그 샘플

### 관할 차이

국내 제21조 제1항은 '보유기간 경과 시 지체 없이 파기'라는 **행위 의무** 중심입니다.
GDPR은 Art.5(1)(e) 원칙 + Art.5(2) **입증책임** 구조라, 파기했다는 사실을 입증할 수
있어야 합니다. **To-Be에서 파기 로그를 남기는 설계는 EU 쪽 요구에서 나옵니다.**

> 참고: A-05(IP)의 인메모리 보관 잔존 시간은 확인되지 않았습니다(U-04). 보유기간
> '미정의'로 분류했으나 확인 후 재평가 대상입니다.

## F-005 · 자유 텍스트를 통한 민감정보 비의도적 수집·국외전송

| | |
|---|---|
| **위험도** | **HIGH** (Likelihood: Medium × Impact: High) |
| 상태 | OPEN |
| 대상 | A-01, A-02, A-03, A-04, B-01 |
| 국내 근거 | `KR-SPC-001` — 개인정보 보호법 제23조 제1항 |
| EU 근거 (조건부) | `EU-SPC-001` — GDPR Art.9(1), Art.9(2), Art.5(1)(c) |

### 확인된 사실

입력 내용을 제한하지 않는 자유 텍스트 채널이 존재하고, 그 입력이 **저장(B-01)과
국외전송(A-01)을 동시에** 거칩니다. 전송·저장 전에 개인정보를 탐지하거나 차단하는 통제가
없습니다.

현재 존재하는 입력 처리는 모두 개인정보 목적이 아닙니다:

| 처리 | 실제 목적 |
|---|---|
| 60자 절단 | 토큰 비용·응답 지연 |
| 무의미 입력 판별 | 판정 품질 |
| `blocked` 판정 | 콘텐츠 안전 — **판정은 전송 이후** 모델이 수행 |

### 리스크 시나리오

이용자가 `"내 우울증을 태워버려"`, `"수술 자국이 아물게 해줘"` 같은 문장을 입력합니다.
게임 특성상 자신의 감정·신체 상태를 문장에 담을 유인이 크고, 판정 프롬프트가 `"배고프다"`,
`"피곤하다"` 같은 상태 표현을 직접 예시로 다루고 있어 이런 입력을 오히려 유도합니다
([worker.js#L71](https://github.com/jaepaly/NHN-Project/blob/852bbd544133f840d972cfc667d17a16618d10db/proxy/worker.js#L71)).

유입된 건강·신념 관련 표현은 탐지되지 않은 채 국외로 전송되고 단말에 영구 저장됩니다.

### 위험도 근거

- Likelihood **Medium** — 유입은 확률적입니다. 다만 프롬프트가 상태 표현을 유도하는 구조라 순수 무작위보다 높습니다
- Impact **High** — 국내 제23조·GDPR Art.9 모두 원칙적 금지 구조입니다. 수집 의도가 없었다는 사정은 예외 사유가 되지 않습니다. 유입 시 전송과 저장이 동시에 발생합니다

### 현재 규모 고려

입력 건수가 적어 유입 확률의 절대량은 낮습니다. 다만 **탐지 수단이 없으므로 유입 여부
자체를 알 수 없다**는 점이 문제이며, 이는 규모와 무관합니다.

### 개선 권고

1. 전송 전 개인정보·민감정보 탐지 및 마스킹 계층 도입
2. 탐지 시 저장 제외 정책 적용
3. 입력창에 민감정보 입력 자제 안내 표시
4. 최소수집 관점에서 **원문 보관 필요성 자체를 재검토** — 판정 후 원문을 버리는 설계가 가장 강한 통제일 수 있음

### 요구 증적

- 탐지 모듈 구현 코드 및 테스트 케이스
- 탐지 정확도 측정 결과
- 입력창 안내 문구 스크린샷

### 관할 차이

**열거 항목이 다릅니다.** GDPR Art.9(1)은 인종·민족적 출신, 유전자정보, 개인 식별 목적의
생체인식정보를 포함하나, 국내 제23조 제1항 본문의 열거(사상·신념, 노동조합·정당 가입·탈퇴,
정치적 견해, 건강, 성생활 등)에는 그 표현이 없습니다.

**탐지 대상 집합을 관할별로 다르게 정의해야 합니다.** To-Be에서 항목 대조표 작성 필요.

## F-004 · 정보주체 권리행사 수단 부재

| | |
|---|---|
| **위험도** | **MEDIUM** (Likelihood: Medium × Impact: Medium) |
| 상태 | OPEN |
| 대상 | B-01, B-02, B-03, B-04, B-05 |
| 국내 근거 | `KR-RGT-001` — 개인정보 보호법 제35조, 제36조 제1항, 제38조 |
| EU 근거 (조건부) | `EU-RGT-001` — GDPR Art.17, Art.12(2) |

### 확인된 사실

**저장소 전체에서 `localStorage.removeItem` 호출이 0건입니다.** 게임 내 데이터 초기화
UI도 없고, 권리행사를 접수할 창구 안내도 없습니다. 이용자가 자신의 입력 이력을 지우려면
브라우저 개발자도구나 사이트 데이터 삭제 기능을 직접 써야 합니다.

### 리스크 시나리오

이용자가 자신이 입력한 문장을 지우고 싶어도 게임 안에서는 방법이 없습니다. 애초에 처리방침이
없어(F-001) 저장 사실 자체를 모르므로, 삭제를 요구할 계기조차 생기지 않습니다.

### 위험도 근거

- Likelihood **Medium** — 권리행사 요구가 발생하기 어려운 구조입니다. 창구가 없어서 요구가 안 들어오는 것을 위험이 낮다고 볼 수는 없으나, 실제 분쟁으로 이어질 빈도는 낮습니다
- Impact **Medium** — 저장 위치가 이용자 단말이라 브라우저 기능으로 물리적 삭제는 가능합니다. 다만 이는 이용자가 저장 사실과 키 구조를 안다는 전제이며, F-001과 결합하면 그 완화가 실효를 잃습니다

### 현재 규모 고려

권리행사 방법·절차 공개 의무는 규모와 무관하게 성립합니다. 다만 실제 요구 건수가 없을
것이므로 실질 위험은 낮습니다.

### 개선 권고

1. 게임 내 저장 데이터 **열람·삭제 기능** 제공
2. 처리방침에 권리행사 방법 및 접수 창구 명시

> 제36조 제1항의 정정·삭제 요구권은 문언상 '제35조에 따라 열람한' 정보주체를 전제합니다.
> 열람 수단이 없으면 삭제 요구의 선행 요건부터 성립하지 않으므로, **열람과 삭제를 함께
> 설계**해야 합니다.

### 요구 증적

- 삭제 기능 구현 코드 및 동작 테스트 결과
- 처리방침 내 권리행사 안내 문구

### 관할 차이

Art.12(2)는 권리 행사를 **용이하게 할 적극적 의무**를 부과합니다. "이용자가 브라우저로
지울 수 있다"는 사실만으로는 충족되지 않습니다.

## F-006 · 연령 확인 수단 부재

| | |
|---|---|
| **위험도** | **MEDIUM** (Likelihood: Medium × Impact: Medium) |
| 상태 | OPEN |
| 대상 | A-01, B-01, B-04 |
| 국내 근거 | `KR-AGE-001` — 개인정보 보호법 제22조의2 제1항 |
| EU 근거 (조건부) | `EU-AGE-001` — GDPR Art.8(1), Art.8(2) |

### 확인된 사실

계정이 없어 이용자의 연령을 확인할 수단이 전혀 없습니다. 아동 접근을 제한하는 장치도
없습니다.

### 리스크 시나리오

초등학생이 브라우저에서 게임에 접속해 자유 텍스트를 입력하면, 그 문장이 국외 LLM으로
전송되고 단말에 영구 저장됩니다. 법정대리인은 이 처리를 인지할 수도, 동의하거나 거부할
수도 없습니다.

### 위험도 근거

- Likelihood **Medium** — 게임은 아동 접근 가능성이 구조적으로 높습니다. 다만 현재는 동의를 처리 근거로 삼는 절차 자체가 없어 제22조의2의 적용 전제(이 법에 따른 동의를 받아야 하는 경우)가 성립하는지가 불분명합니다
- Impact **Medium** — 처리되는 정보의 범위가 제한적입니다. 다만 아동이 입력한 자유 텍스트가 국외로 나간다는 점은 가중 요소입니다

### 현재 규모 고려

실제 아동 이용자 유입은 확인되지 않았습니다. **연령을 알 수 없으므로 유입 여부를 판단할
수 없다는 것 자체**를 미비로 봅니다.

### 개선 권고

1. 연령 확인 절차 설계
2. 만 14세 미만 식별 시 법정대리인 동의 및 **동의 여부 확인** 절차 적용
3. 아동 대상 고지문 별도 작성

> To-Be에서 계정과 동의 절차가 도입되면 이 Finding의 위험도는 상향됩니다. 동의를 처리
> 근거로 삼는 순간 제22조의2의 적용 전제가 명확히 성립하기 때문입니다.

### 요구 증적

- 연령 확인 플로우 설계 문서
- 법정대리인 동의 확인 절차 구현 결과

### 관할 차이

★ **관할 축이 실제 설계를 바꾸는 대표 사례입니다.**

| 관할 | 기준 연령 |
|---|---|
| 국내 (제22조의2) | 만 14세 미만 |
| GDPR (Art.8(1)) | 16세 미만, 회원국이 법으로 **최저 13세**까지 하향 가능 |

국내 기준으로 게이트를 하나 만들면 국내는 충족하지만, **15세 이용자는 국내 통과·EU
미충족**으로 갈립니다. 단일 연령 게이트로는 양 관할을 동시에 만족시킬 수 없으므로
To-Be에서 관할 판별 → 기준 분기 구조가 필요합니다.
